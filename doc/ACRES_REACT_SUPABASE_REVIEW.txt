React + Supabase 전환 시 제외·변경·주의 항목 검토
============================================================================
작성일: 2026-11-09
검토 대상: doc/ACRES_RANK_SYSTEM_DESIGN_V5.txt
           doc/ACRES_RANK_SYSTEM_DESIGN_V5_1.txt
기준: 공통 업무 정책은 두 문서를 함께 검토하고, 화면·메뉴는 v5.1을 기준으로 함.
이 문서는 검토 제안서이며 기존 확정 업무 정책을 변경하는 문서가 아니다.
원본 두 파일은 수정하지 않는다. 아래 장 번호는 별도 표기가 없으면 v5.1 기준.

[검토 전제]
React는 화면, Supabase는 Google OAuth 인증뿐 아니라 PostgreSQL DB와
Data API, DB 함수(RPC), 필요한 Edge Function까지 담당한다고 가정한다.
Supabase Auth만 쓰고 기존 Java/Oracle을 유지한다면 아래 Java/Oracle 제외
판정은 적용되지 않는다. React 도입 자체가 백엔드 제거를 의미하지는 않는다.

[핵심 판단]
현재 업무 기능 중 React + Supabase여서 구현 불가능한 것으로 판단한 항목은 없다.
다만 'React에서 테이블 CRUD만 호출'하는 방식으로는 원문의 원자성·권한·동시성
요구를 충족하기 어렵다. 복합 변경은 DB 함수, 인증 관리자 작업은 서버에서 처리한다.
불필요한 것은 주로 Java/Oracle 전제 및 중복 API 구현이며, 복잡한 업무 규칙은
삭제 대상과 구분해야 한다. 기술 판정은 하단 공식 문서 [1]~[8]과 원문을 바탕으로
한 설계 제안이다. 실제 프로젝트의 처리량·요금제·DB 설정은 검증 범위에 포함하지 않았다.

============================================================================
1. 기존 기술 전제에서 제외하거나 교체할 항목
============================================================================

[A01] Java Backend 필수 전제
원문: 0장 기술 기준, 9장 서비스 레이어, 11장 API, 12장 트랜잭션.
판정: 별도 Java 애플리케이션을 필수 구성에서 제외 가능.
이유: 이 범위는 Supabase Data API와 DB 함수로 구성할 수 있다.[1][2]
대안: React -> Data API/RPC, 인증 관리자 작업 -> Edge Function으로 분리.
주의: '서버에서 검증한다'는 원칙은 유지한다. 검증 위치를 DB/RPC/Edge로 옮긴다.

[A02] Oracle Database 및 Oracle 전용 DDL 전제
원문: 0장 기술 기준, 8장 활성 연맹명 함수 기반 UNIQUE 인덱스, 18장 8번.
판정: Oracle 전용 물리 설계는 교체 필요. Supabase DB는 PostgreSQL이다.[3]
대안: 활성 연맹명은 정규화한 이름에 WHERE status_cd='ACTIVE' 조건의
      부분 UNIQUE 인덱스를 적용하고, 위임 PENDING 1건도 같은 방식으로 제한.[4]
      실제 정규화 규칙은 먼저 확정한다. PK는 uuid 또는 identity 등을 선택한다.
주의: *_SEQ라는 컬럼명이나 숫자 PK가 사용 불가능한 것은 아니다.
      원문에는 물리 DDL이 없으므로 존재하지 않는 Oracle SQL 오류를 단정하지 않는다.

[A03] 11장의 모든 REST 경로를 별도 서버에 그대로 구현
원문: /me, /parties, /alliances, /rank-calendar 및 상태 변경 API 초안.
판정: 독립 REST 서버와 동일 CRUD 경로 전체를 중복 구축할 필요는 낮음.
대안: 안전한 단순 조회/수정은 Data API + RLS, 복합 업무는 이름 있는 RPC 사용.
      예: create_party, apply_to_party, kick_member, accept_alliance_transfer.
주의: 원문 REST 경로는 Supabase가 자동으로 만들어 주는 경로가 아니다.[1]
      상태 전이를 테이블 UPDATE로 아무나 수행하도록 열어서는 안 된다.
      외부 API 계약이 필요해지면 별도 REST 계층을 둘 수 있다.

[A04] USER_SEQ와 SUPABASE_AUTH_UID 이중 식별자 유지
원문: 8장 ACRES_USER(USER_SEQ PK, SUPABASE_AUTH_UID UNIQUE), G04.
판정: 필수 구조가 아니므로 선택적으로 단순화 가능.
대안: 신규 설계에서는 auth UID(uuid)를 업무 회원 PK로 쓸 수 있다.
유지 조건: 탈퇴 후 비개인 관계를 보존하거나 인증 연결을 끊어야 한다면,
           별도 업무 PK + nullable UNIQUE auth UID가 더 적합할 수 있다.
주의: 회원 업무 테이블 자체는 필요하다. 대표 캐릭터·상태·권한을 auth.users나
      브라우저가 수정 가능한 user_metadata에 모두 넣는 방식은 피한다.[5][6]
      PK 통합 여부는 탈퇴/FK 정책 확정 뒤 결정한다.

============================================================================
2. 그대로 적용하기 어렵고 구현 방식을 바꿔야 하는 항목
============================================================================

[B01] OAuth 최초 가입과 회원·첫 캐릭터 생성의 단일 트랜잭션 해석
원문: A05, G04, T01, FL-01, AU-002.
난점: Google OAuth를 마치면 인증 사용자가 먼저 존재하고, 캐릭터 입력은 그 뒤다.
      OAuth 로그인 전체와 이후 사용자 입력까지 하나의 DB 트랜잭션으로 묶지 않는다.
대안: 인증 완료 -> 온보딩 필요 판정 -> 회원+첫 캐릭터+대표 지정을 RPC 1회로 처리.
      실패하면 업무 회원/캐릭터만 롤백하고 인증 사용자는 온보딩 미완료로 취급한다.
      미완료 사용자는 공개 조회·온보딩 등 허용 작업 외 업무 변경을 차단한다.
      재시도 시 auth UID UNIQUE로 중복 가입을 막는다.
판정: 업무 회원+첫 캐릭터 원자성은 유지. 인증 사용자까지 동시 생성된다는 해석만 수정.

[B02] 복수 테이블 변경을 React의 여러 API 호출로 처리
원문: T02, T05~T10, H03, S04, C05.
난점: 파티만 생성되고 OWNER 참여가 실패하거나, 강퇴 후 일정이 남는 부분 성공 가능.
      Edge Function 안에서 SDK 요청을 여러 번 보내도 자동으로 한 트랜잭션이 되지 않는다.
대안: 업무 명령별 DB 함수 안에 권한·현재 상태 확인, 변경, 오류 시 롤백을 묶는다.[2]
      예: 파티 생성/교체/강퇴/연맹 탈퇴/해체/위임 수락을 각각 원자적 명령으로 설계.
판정: 원문의 원자성 요구는 유지. 브라우저 순차 CRUD 구현은 제외.

[B03] OWNER 최소 캐릭터 1개·대표 캐릭터 1개·재신청의 동시성
원문: A02, B06/R11, B08, T03/T05/T06, 18장 3번.
난점: '현재 2개니까 하나 삭제 가능' 검사 두 건이 동시에 통과하면 0개가 될 수 있다.
      사전 중복 확인이나 일반 RLS만으로 여러 행 사이의 불변식을 보장하기 어렵다.
대안: 파티/회원 등 공통 기준 행을 잠그고 검증·변경하며 모든 변경 경로에 같은 규칙 적용.
      신청 UNIQUE(파티,회원), 참여 UNIQUE, 일정 UNIQUE 및 CHECK/FK를 DB에 설정.
      동일 파티+캐릭터 유일성도 React 사전 조회만으로 검증하는 선택지는 제외한다.
      구조상 유일성이 보장되는지 확인하고 필요하면 복합 FK/UNIQUE를 사용한다.
판정: 유지 필수. DB 동시성 설계와 직접 변경 경로 차단 필요.

[B04] 계층별 복잡한 권한과 즉시 권한 회수
원문: C02~C06, D07/D11, E03, H10, 10장, 17장 공통 원칙.
난점: 내 행만 수정 허용하는 정책으로는 승인·강퇴·공지·관리자 예외를 표현하기 부족하다.
      ROLE_CD/IS_MANAGER_YN/신청 상태를 자유롭게 수정할 수 있으면 권한 상승 가능.
대안: 조회는 RLS, 민감한 상태 전이는 권한 검증 RPC로 제한하고 직접 DML 권한을 통제.
      매 요청에서 auth.uid()를 기준으로 업무 회원·현재 역할·연맹 자격 확인.
      회원 테이블의 자기 행 UPDATE 허용도 수정 가능 컬럼을 제한한다.
      즉시 회수할 권한은 오래된 JWT 역할/소속 정보만 믿지 않고 현재 DB 상태로 확인.[5]
      관계 테이블을 다시 조회하는 RLS는 재귀 정책이 생기지 않도록 설계한다.
      SECURITY DEFINER가 필요하면 호출자 검증, 실행 권한, search_path를 제한한다.[2]
판정: 권한 규칙 유지. React 라우트/버튼 숨김만으로 구현하는 방식은 제외.

[B05] 연맹 탈퇴·강퇴·해체에 따른 여러 파티 즉시 정리
원문: D09/D10, H04/H10, T08/T09, AC-09.
난점: 관련 파티/캐릭터/일정을 함께 처리해야 하고 파티 신청과 경쟁할 수 있다.
대안: DB 함수에서 연맹과 관련 행을 일관된 순서로 잠그고 일괄 처리한다.
      연맹 탈퇴·신청·승인 경로가 같은 잠금 규칙을 따르도록 한다.
      관련 규모가 커지면 쿼리/인덱스와 실행 시간을 검증한다.
주의: 비동기 작업으로 바꿀 때는 '즉시 제거·실패 시 전체 롤백' 정책 변경 검토가 필요.
판정: 구현 가능하지만 난도가 높다. 단순 CASCADE 삭제나 화면 후처리로 대체하지 않는다.

[B06] 연맹장 위임 상태와 소유자 중복 정보
원문: D03/D04, H05, R05/R06, 8장 OWNER_USER_SEQ 및 MEMBER.ROLE_CD, T10.
난점: 요청 수락·취소·대상 탈퇴가 경쟁하고, 소유자 컬럼과 역할 행이 어긋날 수 있다.
대안: 연맹·현재 요청 잠금 후 현재 연맹원 자격/요청 상태/당사자를 재확인한다.
      새 소유자와 양쪽 역할을 한 RPC에서 갱신하고 PENDING은 부분 UNIQUE로 제한.
      중복 역할 정보를 유지하면 일관성 보장 경로를 명확히 한다.
판정: 업무 기능 유지. 프런트에서 역할을 순서대로 변경하는 구현은 제외.

[B07] 계정 탈퇴·비식별화와 Supabase Auth 삭제
원문: A04, R12/S05, 7장, T12, MY-003, 18장 5번.
난점: 업무 DB 정리와 Auth 관리 API 호출 전체의 원자적 성공을 가정할 수 없다.
      인증 사용자 삭제만으로 업무 관계·공지·캐릭터 식별정보 정리가 완료되지 않는다.
대안: 인증된 탈퇴 요청을 Edge Function 등 서버에서 처리. 탈퇴 진행 상태로 업무 접근을
      막고, 선행 소유권 정리 검증 -> 업무 데이터 정리 -> Auth 삭제를 재시도 가능하게 설계.
      중간 실패를 위한 최소 처리 상태는 업무 변경 이력과 구분한다.
      Admin API 키는 React 환경변수/번들에 넣지 않는다.[7]
      Auth 삭제 후에도 기존 access token 만료 전 상황을 고려해 접근 차단을 유지한다.[6]
      auth.users FK의 CASCADE로 보존할 관계까지 사라지지 않도록 설계한다.
판정: 삭제 대상 아님. 보존/익명화/FK 정책과 실패 복구가 확정되어야 구현을 마칠 수 있음.
      이 문서는 보존 기간이나 법적 적정성을 새로 판정하지 않는다.

[B08] 날짜·마감 검증 및 '권한 없음=항상 HTTP 403' 가정
원문: E06/E08, R02/R07, S01, T03/T11, 15장 공통 예외, 18장 1번.
난점: 브라우저 시간/기본 DB 타임존을 쓰면 KST 당일·마감 경계가 달라질 수 있다.
      RLS 조회 차단은 빈 결과가 될 수 있어 모든 권한 실패가 HTTP 403은 아니다.[5]
대안: 출발일/전쟁일은 date, 마감은 timestamptz로 설계하고 DB 기준 현재 시각으로 검증.
      KST 오늘 날짜와 출발일~+11일 범위를 명시하며 마감 시각 동일 요청 정책을 확정.
      RPC 업무 오류와 Data API 오류를 화면용 오류 코드로 매핑한다.
      일정 조회 실패/권한 없음/로딩 중을 '행 없음=FULL'로 처리하지 않는다.
판정: 업무 날짜 규칙은 유지. 화면 시간만 신뢰하거나 HTTP 상태를 일률 가정하는 명세는 수정.

============================================================================
3. 불필요하거나 현재 범위에서 만들지 않아도 되는 항목
============================================================================
아래 C01~C05는 원문이 이미 제외한 기능을 구현 범위에서도 제외하라는 의미다.
현재 설계서에 해당 기능이 요구되어 있다는 뜻은 아니다.

[C01] 공지 파일·이미지 업로드 및 Supabase Storage
근거: F05, PT-006, AL-004. 제목/본문 텍스트만 필요하므로 버킷/업로드 기능 불필요.
      별도 이미지 기능을 추가하지 않는 한 현재 범위에 넣지 않는다.

[C02] 공지 읽음 여부/읽음 사용자 집계
근거: F03. 읽음 테이블, 수신 확인 UI, 읽음 추적 이벤트 불필요.

[C03] 업무 감사·신청 과거 버전 테이블
근거: B08, G02/G09, S02. 신청/참여 현재 행을 재사용하므로 버전 이력 추가 불필요.
      생성/수정 시각과 플랫폼 인증·운영 로그, 탈퇴 복구용 처리 상태는 별개다.

[C04] 랭크 일정 자동 생성 배치 및 파티 출발일 강제 연동
근거: G07/G08, FL-08, RC-001. ADMIN 수동 관리이며 파티 날짜와 독립.
      이를 위한 3일 주기 Cron이나 파티 날짜 FK 제약은 필요 없다.

[C05] 12일 FULL 일정 사전 생성·PARTIAL 시작/종료 시각·실제 종료 추적
근거: E04/E06/E08. 예외 일정만 저장하므로 전 캐릭터 12일 행 선생성 불필요.
      PARTIAL 메모는 필요하지만 별도 시간 컬럼과 실제 종료일/조기 종료 기능은 불필요.

[C06] 화면 ID마다 독립 페이지·별도 관리자 화면 복제
근거: 14장 메뉴 원칙, 16장 PT-003-A/B 및 AD-001.
판정: 화면 ID는 설계 식별자이므로 ID마다 별도 URL/컴포넌트를 만들 필요 없음.
대안: 파티/연맹 상세의 탭과 권한별 버튼 재사용. 필요 경계에 맞춰 React 컴포넌트 분리.
      AU-001/002를 별도 로그인 백엔드로 해석하지 않고 Google OAuth + 온보딩으로 구현.

[C07] 홈·내 정보의 중복 요약, 고급 필터, 여러 날짜 일괄 적용
근거: HM-001/MY-001, PT-001, PT-005, 17장 미확정 UI 선택지.
판정: Supabase 적용이 어렵지는 않다. 원문상 설계 제안이므로 초기 버전에서 축소 가능.
대안: 홈 요약을 줄이고 내 캐릭터/내 파티/내 연맹 진입과 기본 목록·단일 날짜 편집 우선.
      접근성·기본 반응형·오류 안내까지 불필요하다는 뜻은 아니다.

[C08] 무조건적인 Realtime 구독 추가
근거: 17장 2번은 작업 성공 후 재조회만 요구하며 상시 실시간 동기화는 명시하지 않음.
판정: 모든 테이블 Realtime 구독을 초기 필수 기능으로 추가할 필요 없음.
대안: 작업 후 재조회/캐시 무효화, 화면 복귀 시 재검증으로 시작.
      서버의 권한 회수는 즉시 반영해야 하지만 다른 브라우저 UI 동기화는 별도 요구다.
      이미 내려받은 정보를 권한 회수로 소급해서 회수할 수 있다고 보장하지 않는다.

============================================================================
4. 복잡하다는 이유로 제외하면 안 되는 항목
============================================================================
- A01~A05 회원/캐릭터 및 대표 캐릭터 규칙: RPC와 DB 제약으로 구현 가능.
- 회원 단위 신청 -> 승인 후 복수 캐릭터 참여: 핵심 정책이며 캐릭터별 신청으로 바꾸지 않음.
- 본인 제외와 관리자 제외/재승인 구분: 상태 모델이 필요하며 단일 삭제 상태로 합치지 않음.
- 병종 0~2개, 참여별 독립 설정, 12일 예외 일정: 관계형 DB에 적합한 요구.
- 일반/연맹 전용 접근, 강퇴 차단·해제, OWNER 보호: RLS와 RPC로 보장해야 함.
- 출발 후 직접 링크 신청, 마감 후 기존 PENDING 승인: 날짜 편의상 일괄 차단하지 않음.
- 해체 파티/연맹의 내 목록 표시: 일반 목록 필터와 개인 과거 목록 권한을 구분.
- 인원 상한 없음: 업무 정원 제한이 없다는 뜻. 페이지네이션·조회 범위 제한은 필요.
- ADMIN 지정 통제, 개인정보 처리, 보안 로그 구분: 기술 변경 후에도 유지.

============================================================================
5. 구현 전에 먼저 결정해야 할 항목
============================================================================
원문이 미확정이라고 밝힌 사항은 Supabase 기능만으로 답이 정해지지 않는다.

1) 비로그인 공개 조회와 연맹 전용 검색 노출 범위: RLS SELECT 정책의 전제.
2) LEFT/KICKED 회원의 해체 목록·공지·상세 열람 범위: 기존 참여자 권한 정의 필요.
3) 마감 시각 동일 요청·과거 마감 생성 허용 여부: DB 검증식의 전제.
4) 관리자 제외 캐릭터의 재승인 담당자·거절 상태: RPC 권한/전이 확정 필요.
5) 개인정보 보존/정리 방식, 재가입과 auth UID 연결: 회원 PK/FK 설계의 전제.
6) 연맹명 정규화, 병종 목록, 최대 길이, 날짜 중복: CHECK/UNIQUE/마스터 확정 필요.
7) ADMIN의 마감 수정 가능 여부: R07/PT-003은 생성자만, 3장은 ADMIN 전체 관리로
   읽힐 여지가 있어 실제 예외 범위를 명시해야 한다.

권장 구성:
React 화면 + Supabase Auth + PostgreSQL 테이블/제약 + RLS 조회 정책
  + 복합 변경용 RPC + Auth 관리자 작업용 Edge Function.
SQL 마이그레이션으로 스키마·정책·함수를 관리한다.
이 검토서는 앱 구현, DB 변경, Supabase 배포를 수행한 결과가 아니다.
